# 故事映射成导演台

故事板格式：`format: ludo-storyboard`、整数 `version: 1`、`name`、`content`，可选 `notes` 与 `character_notes`。`notes` 为作者需要复核的推断列表，不进入工程叙事；随故事板一起交付。`character_notes` 是人物 ID → 简短备注。它们与 NPCs AI Studio 工程 v2 不同，不能直接从项目菜单打开故事板。

`content` 支持 `world/characters/locations/factions/facts/variables/events/rules/dialogues/texts/relations/levels/initial_state`。集合为数组，字段与项目 Schema 对应；可省略空集合，不携带模型配置、草稿、生成或试玩历史。不要夹带自由定义字段。脚本自动添加基础展示布局。

| 故事概念 | NPCs AI Studio 映射 | 注意点 |
| --- | --- | --- |
| 故事背景、写作规则 | `world.premise/rules/tone` | 正式规则和创作建议分清 |
| 章节/关卡 | `levels[]` | 一个关卡可以有多场景、多次登场 |
| 营地、医帐等场所 | `locations[]` + `level.tracks[]` | track 引用 location，场景位置不等于人物档案 |
| 入场、黄昏、警报等阶段 | `level.anchors[]` | 每个阶段有整数 tick；轴模式 `phase` 或 `time` |
| 角色 | `characters[]` | ID 稳定，身份用 role，快速记忆用备注 |
| 人物在特定时地出现 | `level.appearances[]` | 人物、track、起止时间、明确对白 ID |
| 篝火旁的三位村民 | `level.npc_groups[]` + 三个人物和三次出场 | 每个成员写自己的对白，非一段多说话人文本 |
| 人物关系 | `relations[]` | 两端为 `{kind,id}`，互相认识不等于知识共享 |
| 受伤/好感/警戒状态 | `variables[]` | boolean、number、text，初始值类型准确 |
| 条件事件/后果 | `events[]/rules[]` | scope 引用关卡/track；目前规则每轮预演一次 |
| 玩家交谈 | `dialogues[]` | 默认入口、卡片、选项、条件、效果和跳转 |
| 信件/传言/日记 | `texts[]` | body 与出现条件；不当成角色 |
| 谁知道秘密 | `facts[]` + 初始知识/知识效果 | private 是作者标记，不是自然语言过滤器 |

时间处理：先采用作者已有单位。只有阶段时可使用 chapter/phase 的顺序 tick，注明这是顺序刻度而非真实分钟。不要把多个关卡的局部时间误当不同时间域；执行器使用统一故事 tick。出场区间端点可同时有效，跨场景连续安排时明确边界，避免同一人物误重叠。

对白处理：`entry_node_id` 通常是开场。某个选项需要受伤时，条件写在该 `options[]` 项上；治疗后效果写在选项或治疗卡片上，选择一种执行时机，避免重复效果。`target_node_id: null` 表示结束。`entry_routes[]` 只在作者希望开场根据状态变化时使用。

对话跟随出场：开场卡片的条件可写 `{op: appearance, level_id: ..., appearance_id: ...}`，该出场的 `dialogue_ids` 写对应图 ID。对出场区间、场景与附加条件的校验由 Python 执行。空 `dialogue_ids` 有旧版默认包含人物/通用对白的含义，不用它表达“没有对白”。

至少为一次关键对话设计普通状态与条件满足两份测试；优先使用简单默认入口，保留玩家自主选择。自由文本的质量、世界观矛盾和泄密需要作者复核，Schema 校验不能代替它。

用户提供小说时，可提取主要关卡而不逐句搬运。保留影响行为的动机和关系；没有玩法作用的细节放故事字段。无法明确转成当前条件/效果的机制保留为作者说明，不发明执行器操作名。

项目层级：世界底稿只放全局背景、规则与风格。每个关卡的 `region` 填所属区域，`description` 填当地背景、剧情阶段与主要冲突；人物档案在项目中共享，场景引用人物安排出场。不要将关卡地域写入旧字段 `world.district`。

## 对白数量与长度

“每人对白卡片数”指每个人的一份对白图中的 `nodes` 总数，包含开场和全部分支卡片，不是句子数、玩家选项数或人物数。一张卡片可以有多个句子。NPC 组每个成员有自己的对白图，不能在一份候选里混入多个 NPC 说话。

例如 4 个 NPC、每人 2 张卡片：交付 4 份逐人对白候选，共 8 张卡片；某人有开场和治疗分支，就已经占满其 2 张。结束可用玩家选项的 `target_node_id: null`，不必另加告别卡片。数量不能代替完整的跳转与效果检查。

控制台场景生成支持每人 1–6 张（默认 2），每张正文可选简短 120、适中 240、详细 480 个 Unicode 字符，包含标点与空格，不包含玩家选项文字。匿名环境文本按每份正文长度计算，不设置卡片数，也不创建人物。作者未指定规模时，普通背景 NPC 可建议 2 张简短卡片；关键剧情按实际需求约定，不将场景生成的范围当作整个项目的限制。修改既有对白时保留未涉及的卡片，不为套用默认数量删除分支。

创作前说明人数、每人卡片数、总卡片数和长度，输出后按每个人实际 `nodes` 数量与 `text` 长度复核。不要为了满足数量截断文本、留下断开的跳转或删去必要效果；调整结构或说明需要重新约定规模。英文同样按字符计数，不按单词计数。

`GenerationItem.output_limits` 的 `card_count/text_length` 仅属于平台模型生成请求，精确字段见运行服务的 `/openapi.json`；不能塞进故事板、实体 `patch` 或桥接提案。平台会校验带限制的模型输出并收紧单项输出 tokens 上限，数量/长度不合格时不自动调用模型修补；失败也可能已消耗用量。输出上限不是实际用量或费用估算。外部 AI 通过本 Skill 创作时自行检查规模；桥接的工程结构校验不代替这项检查，也不会再调用平台模型。重试平台任务只处理失败项并沿用原限制，保留成功候选。
